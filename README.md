# EMA Crossover: перенос стратегии из Pine Script на Python

[![tests](https://github.com/FuR1DeV/pine-ema-bybit/actions/workflows/tests.yml/badge.svg)](https://github.com/FuR1DeV/pine-ema-bybit/actions/workflows/tests.yml)

Скрипт `solution.py` воспроизводит стратегию TradingView «EMA Crossover» (Pine Script v5, EMA 9 и EMA 21) на асинхронном Python и прогоняет её на реальных минутных свечах BTCUSDT со спота Bybit.

Что он делает по шагам:

1. Асинхронно (httpx) одним запросом берёт последние 1000 минутных свечей: `GET /v5/market/kline`, `category=spot`, `symbol=BTCUSDT`, `interval=1`, `limit=1000`.
2. Чистит данные: порядок, незакрытая свеча, битые бары, дубли, пропуски минут.
3. Считает EMA и пересечения на numpy/pandas, без библиотек теханализа, по тем же правилам, что `ta.ema`, `ta.crossover` и `ta.crossunder`.
4. Торгует Spot Long-only: сигнал по Close бара T, сделка по Open бара T+1, вход 1000 USDT, комиссия 0.1% на вход и 0.18% на выход.
5. Печатает сводку очистки, список сделок и итоговую статистику.

## Запуск

Нужен Python 3.11+. Проверено на 3.11.18 и 3.12.3: зависимости ставятся, тесты проходят, вывод одинаковый. В CI тесты идут на 3.11, 3.12 и 3.13.

```bash
python3.11 -m venv .venv
.venv/bin/pip install -r requirements.txt
.venv/bin/python solution.py
```

Тесты (сеть не нужна, ответы Bybit синтетические) и линтер:

```bash
.venv/bin/pip install -r requirements-dev.txt
.venv/bin/python -m pytest -q
.venv/bin/ruff check . && .venv/bin/ruff format --check .
```

## Данные: что чистим и почему

Всё сделано в `clean_klines`, там же комментарии. Свечи приходят массивами строк `[startTime, open, high, low, close, volume, turnover]`.

| Что | Что делаем | Почему |
|---|---|---|
| Ошибка API | проверяем `retCode`, при `!= 0` выходим с ошибкой | Bybit отдаёт ошибки с HTTP 200, по статусу их не видно |
| Сеть, 5xx | до 3 попыток с паузой | разовый сбой не должен ронять запуск; 4xx не повторяем |
| Обратный порядок | сортируем по `startTime` | Bybit отдаёт от новых к старым, EMA считается от старых к новым |
| Незакрытая свеча | отбрасываем, если `startTime + 60 с > time` | её Close ещё меняется, а сигнал считается строго по закрытию бара. Время берём из поля `time` ответа (часы сервера Bybit), а не локальные часы |
| Битые свечи | удаляем: цена `<= 0` или не число, `high < low`, open/close вне `[low, high]`, время не кратно минуте | настоящих цен мы не знаем, а придуманная цена может дать ложное пересечение |
| Дубли `startTime` | оставляем первую копию | битые удаляем раньше дублей, чтобы битая копия не вытеснила нормальную |
| Нераспознанные строки | удаляем | не хватает полей или не число |
| Пропуски минут | считаем и печатаем, не заполняем | TradingView рисует бар только там, где были сделки, и считает EMA по существующим барам. Если дорисовать пустые минуты, у нас будут бары, которых нет у TV, и EMA разойдётся с графиком |

Если сделка исполняется после пропуска (бар T+1 пришёл не через минуту), сделка помечается «вход/выход после пропуска минут».

## EMA и пересечения

- `alpha = 2 / (length + 1)`, `ema[i] = alpha * close[i] + (1 - alpha) * ema[i-1]`.
- Засев (`--ema-seed sma`, по умолчанию): первые `length - 1` значений пустые (na), первое значение равно SMA первых `length` закрытий. Так ведёт себя встроенная `ta.ema` на графике: EMA 21 появляется только с 21-го бара истории. В справке Pine есть пример `pine_ema`, который засевает первым значением источника; этот вариант доступен как `--ema-seed first`. Какой засев точнее повторяет TV, на сигналы после прогрева не влияет (ниже показано на данных).
- `crossover(a, b)`: `a > b` на текущем баре и `a <= b` на предыдущем. `crossunder` зеркально. Сравнение с na даёт false, поэтому на первом баре, где появилась EMA, сигнала нет. Касание тоже считается: если EMA сравнялись, а потом быстрая ушла выше, это crossover, как в Pine.

## Прогрев EMA и расхождения с TradingView

Главная причина расхождений. На графике TradingView у EMA длинная история: к нашему первому бару она уже посчитана по тысячам предыдущих баров. У нас всего 1000 баров, и EMA начинается с засева. Первые значения EMA у нас и у TV разные, значит и пересечения в начале данных могут быть другими.

Разница засева затухает: на каждом баре она умножается на `1 - alpha`. Для EMA 21 это `(1 - 2/22)^n`, после 210 баров множитель около `2e-9`. Даже если засев ошибся на 1000 USDT, через 210 баров останется 0.000002 USDT, это намного меньше шага цены BTCUSDT на споте Bybit (0.1, `tickSize` из `/v5/market/instruments-info`). Быстрая EMA 9 затухает ещё быстрее.

Поэтому первые `10 * slow = 210` баров (3.5 часа) скрипт не торгует. Сигналы оттуда считаются и печатаются отдельно с пометкой «могут отличаться от TV». Начиная с 211-го бара EMA совпадает с «длинной» EMA точнее шага цены, и сигналы должны совпадать с графиком TV, если совпадают сами свечи.

Проверка на данных из примера: разница между засевами `sma` и `first` у EMA 21 в момент засева 28.09 USDT, к 105-му бару 0.0085 USDT, после 210-го бара меньше 0.000001 USDT. Сигналы двух вариантов различаются только на барах 1 и 12 (внутри прогрева), сделки одинаковые. Тест `test_warmup_hides_seed_difference` проверяет то же самое на синтетике: EMA по 3000 барам («как у TV») и по последним 1000 («как у нас») после прогрева отличаются меньше чем на 0.01, сигналы совпадают.

### Сверка бар за баром: `compare_tv.py`

Скрипт сравнивает наши 1000 баров с эталоном, у которого длинная история, по времени открытия бара: сами свечи, значения EMA в прогреве и после него, сигналы. Эталонов два.

1. Выгрузка графика TradingView. На `BYBIT:BTCUSDT` (спот, 1m) добавить `tradingview/ema_crossover_export.pine`: это исходная стратегия плюс два `plot` с EMA, чтобы значения попали в Export chart data. Затем:

   ```bash
   .venv/bin/python compare_tv.py --tv export.csv --raw examples/bybit_spot_BTCUSDT_1m.json
   ```

   Время в выгрузке может быть UNIX или ISO с часовым поясом, скрипт понимает оба. Если стрелок BUY/SELL нет в выгрузке, сигналы TV пересчитываются по EMA самого TV.

2. Длинная история самого Bybit, без TradingView: 3000 баров, кончающихся на нашем последнем баре (несколько запросов с параметром `end`), та же стратегия на них. Так EMA видит историю, как на графике TV.

   ```bash
   .venv/bin/python compare_tv.py --bybit-history 3000
   ```

Результат второго варианта на данных из примера (эталон начинается 17.11 10:47 UTC, за 33 часа до наших данных):

```text
  баров у нас: 999, у эталона в том же интервале: 999, общих: 999
  свечи с другими ценами: 0
  EMA 9: макс. разница в прогреве 1.200964, после прогрева 0.000000
  EMA 21: макс. разница в прогреве 27.750952, после прогрева 3.8e-07
  сигналы в прогреве: баров с расхождением 1 (ожидаемо, засев)
  сигналы после прогрева: у нас 30, баров с расхождением 0
```

То есть в прогреве EMA 21 отличается от «длинной» почти на 28 USDT, а после него меньше чем на 0.000001. Все 30 сигналов после прогрева совпадают. Если прогрев отключить (`--warmup 0`), всплывает ровно то расхождение, от которого он защищает: у эталона SELL в 20:20, а у нас его нет, потому что наша EMA 21 появляется только в 20:28.

Другие возможные расхождения с TradingView:

- Текущий бар. На графике TV `plotshape` рисует сигнал и на незакрытом баре, и он может исчезнуть до закрытия. Мы незакрытый бар отбрасываем, поэтому такого сигнала у нас нет.
- Сами свечи. Если свеча на графике `BYBIT:BTCUSDT` отличается от ответа API (например, биржа поправила бар), EMA разойдётся на несколько длин slow.
- Удалённые битые бары. У TV этот бар есть с реальными ценами, у нас его нет. EMA после него расходится, пока не затухнет, как при засеве. В примере таких баров 0.
- Почти равные EMA. Если быстрая и медленная отличаются на уровне погрешности float, знак разницы может зависеть от порядка вычислений. Pine тоже считает в float64, такое маловероятно.

Если нужно сравнить по-своему, `solution.py --csv bars.csv` выгружает наши бары с EMA, сигналами и пометкой прогрева.

## Исполнение

- Сигнал бара T известен только после закрытия бара, поэтому сделка идёт по Open бара T+1. Цикл бэктеста на баре T смотрит только на сигнал бара T и цену открытия бара T+1, в будущее не заглядывает.
- Long-only: BUY без позиции открывает позицию, SELL в позиции закрывает её в кэш. BUY в позиции и SELL без позиции игнорируются и считаются в итоге.
- Сигнал на последнем баре исполнить нечем, бара T+1 ещё нет. BUY пропускается (с сообщением в итоге). SELL при открытой позиции закрывает её по Close последнего бара, то есть так же, как принудительное закрытие.
- Если на конец данных позиция открыта, она закрывается по последней цене (Close последнего закрытого бара) и попадает в список с пометкой.
- Проскальзывание: `Open(T+1) / Close(T) - 1` для входа и для выхода. Если по модулю больше 0.5%, в консоль печатается предупреждение, а у сделки появляется отметка. Для принудительного закрытия проверки нет: там цена исполнения и есть последняя цена.

## Комиссии и PnL

Комиссия берётся от фактической суммы каждой сделки:

```text
вход:   комиссия = 1000 * 0.1% = 1 USDT, монет куплено qty = (1000 - 1) / цена входа
выход:  выручка = qty * цена выхода, комиссия = выручка * 0.18%
PnL     = выручка - комиссия выхода - 1000 USDT,  PnL % = PnL / 1000
```

Пример: вход 100, выход 110. Куплено 9.99 монеты на 999 USDT, выручка 1098.90, комиссия выхода 1.98, PnL +96.92 USDT (+9.69%). Сделка без движения цены теряет 2.80 USDT (0.28%). Winrate считается как доля сделок с чистым PnL > 0, то есть после комиссий.

## Ограничения

- 1000 минутных свечей это около 16.5 часов, из них 3.5 часа уходят на прогрев. Для оценки стратегии этого мало, задание про перенос логики, а не про доходность.
- С выгрузкой самого TradingView бар за баром я не сверял: на моём бесплатном тарифе TradingView нет выгрузки данных графика. Довод про прогрев проверен на эталоне из длинной истории Bybit (раздел «Сверка бар за баром»). Скрипт и Pine-файл для сверки с выгрузкой TV готовы, это одна команда.
- Деньги в float. Для бэктеста этого хватает. Для реальных ордеров нужны Decimal и правила биржи: шаг количества и цены, минимальная сумма ордера.
- Проскальзывание здесь только разница между Close сигнального бара и Open следующего. Реальное зависит от стакана и размера ордера.
- Комиссии фиксированные, как в задании. У Bybit они зависят от уровня аккаунта и от того, maker ордер или taker.
